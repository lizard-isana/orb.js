# orb.js 3.2 documentation-driven release plan

Status: Accepted direction / scope collection

Target release: `@lizard-isana/orb@3.2.0`

Integration branch: `v3`

Release branch: `release/3.2`, created only at code freeze

Implementation status: not started. This plan records the accepted release
direction and the gates for selecting work; it does not authorize unrelated
feature expansion.

## 1. Release intent

Version 3.2 is a backward-compatible minor release centered on the detailed
orb.js manual and on focused corrections discovered while that manual is
reviewed. The documentation work is expected to expose ambiguous names,
underspecified contracts, missing package checks, and genuine mismatches
between documented meaning and runtime behavior. Version 3.2 may correct those
problems when the correction is compatible, testable, and useful independently
of the documentation site.

This is not a general feature release. Documentation review is a source of
evidence and scope, not a reason to redesign every API it describes.

The intended outcome is:

1. retain the reviewed 3.1.1 manual content as a private, reproducible baseline
   and inventory its findings;
2. accept a bounded 3.2 code scope from those findings;
3. implement compatible corrections on `v3`;
4. provide one exact 3.2 candidate artifact to the documentation work and
   receive verification against that same artifact; and
5. release the 3.2 package and the first public detailed manual as one
   coordinated release.

## 2. Baseline and repository boundaries

- `@lizard-isana/orb@3.1.1` is the current stable package baseline.
- `orb.js` owns runtime behavior, package exports, package-local quick-start
  documents, migration records, release notes, and the npm artifact.
- `orb.js-docs` owns the detailed bilingual manual, semantic API contracts,
  runnable documentation examples, navigation, search, and hosted site.
- The detailed manual remains pinned to an exact package artifact. It must not
  describe an unreleased 3.2 API as stable.
- Package-local documents remain concise and package-centered. Detailed
  explanations belong in `orb.js-docs` and are linked from the package.

The existing 3.1.1 manual content is the reviewed baseline for discovering and
classifying changes, but it is not published first as a separate stable manual
release. The first public detailed manual targets 3.2 and launches as part of
the coordinated 3.2 release. The 3.1.1 snapshots and provenance remain intact
as evidence; they are not overwritten by generated 3.2 facts.

The documentation work is owned by its separate thread and plan. This code-side
plan does not edit or schedule internal `orb.js-docs` tasks. Coordination occurs
through explicit handoffs:

- orb.js provides the candidate version, source commit, artifact checksum or
  integrity, packed file list, export inventory, release notes, and tarball;
- the documentation work reports the exact artifact it consumed, automated
  check results, example results, representative visual review, and production
  readiness; and
- both sides record the same final version and provenance before the release is
  considered complete.

## 3. Branch and version policy

### 3.1 `v3` is the 3.2 integration branch

All work specific to the backward-compatible 3.2 minor release is integrated
on `v3`. Work may use short-lived topic branches, but `v3` is the authoritative
pre-freeze integration line.

Do not change `package.json` to `3.2.0` merely to begin development. The exact
release or prerelease version is applied during release preparation.

### 3.2 Changes that also belong in 3.1

A documentation correction or defect fix needed by the supported 3.1 line
starts on `release/3.1`, is verified there, and is forward-ported as a focused
commit to `v3`. A real 3.1 contract defect that should not wait for 3.2 belongs
in this path.

New public names or other compatible additions intended specifically for 3.2
are implemented only on `v3`.

### 3.3 Code freeze and publication

After the accepted scope is complete and verified, cut `release/3.2` from
`v3`. Release-only corrections are made there and forward-ported to `v3` when
they remain applicable. Publish and verify the exact release artifact under
the npm `next` dist-tag before advancing `master` and promoting the same
version to `latest`.

## 4. Scope policy

### 4.1 In scope

- receiving and classifying code-relevant findings from the detailed-manual
  review;
- corrections to names, descriptions, units, frames, centers, time scales,
  model identities, validity ranges, defaults, errors, and result shapes that
  are discovered through documentation review;
- backward-compatible public aliases when a clearer canonical name materially
  improves the contract;
- focused runtime fixes for a demonstrated mismatch between the documented
  contract and implementation;
- tests required to preserve compatibility and prove the corrected contract;
- package metadata, exports, examples, release notes, and migration guidance
  required by an accepted 3.2 change;
- producing and identifying the exact 3.2 package artifact consumed by the
  manual;
- package-local links and release coordination with the externally owned
  detailed-manual release; and
- maintenance work required for a safe, reproducible 3.2 release.

### 4.2 Initial accepted candidate

The first accepted 3.2 API candidate is the structured two-body propagator
name:

```js
export function propagateTwoBody(r0, v0, dt, mu, options = {}) {
  // existing implementation
}

export const propagateKepler = propagateTwoBody;
```

The intended contract is:

- `propagateTwoBody` is the preferred descriptive name;
- `propagateKepler` remains a supported compatibility alias, not a deprecated
  API;
- both names refer to the same function object;
- numerical behavior, defaults, units, input acceptance, results, and failure
  conditions remain unchanged; and
- package, tarball, source, and documentation checks cover both names and
  record their alias relationship.

Before implementation, record the observable effect on `Function#name` and
decide how existing `propagateKepler:` diagnostic prefixes are presented. Do
not change error types or messages casually as part of the rename.

Implementation remains deferred until the detailed-manual review is complete
enough to assess this change together with the rest of the 3.2 findings.

### 4.3 Explicitly out of scope

- the semantic traceability experiment, its PoC, trace schema, collector,
  package exports, or shared-operation architecture;
- work from `archive/v4-prototype` or a revival of that implementation;
- breaking removals or changes to existing API shapes, defaults, units,
  coordinate semantics, synchronous behavior, or legacy compatibility;
- unrelated new astronomical models, datasets, event types, or visualization
  features;
- broad refactors justified only by aesthetic preference;
- publishing package-private helpers merely to make them easier to document;
  and
- changing numerical results without references, regression fixtures, and an
  explicit compatibility review.

Traceability remains release-unassigned research. A later decision may place a
validated form in another v3 minor, a v4 design, or nowhere; it is not a 3.2
dependency or release gate.

## 5. Documentation finding intake

Every proposed runtime or public-API change discovered during manual review is
recorded before implementation with:

- the page, example, contract entry, or review that exposed it;
- current observable behavior in 3.1.1;
- the intended astronomical meaning and JavaScript contract;
- classification as documentation-only, 3.1 fix, or 3.2 compatible change;
- compatibility impact, including reflective and error behavior where
  relevant;
- required source, package, and documentation tests;
- package-size or performance implications; and
- release-note or migration impact.

Accept a finding into 3.2 only when it meets all of these conditions:

1. The problem can be stated independently of prose preference.
2. The proposed result is backward compatible for existing callers.
3. The change has a bounded implementation and verification surface.
4. The detailed manual can describe one clear canonical contract afterward.
5. The benefit justifies adding or changing a long-term public commitment.

Documentation-only findings should normally be fixed in the documentation
project rather than turned into runtime work; hand them back to the
documentation thread. A true defect affecting 3.1 is routed through
`release/3.1`; it is not relabeled as a 3.2 feature.

## 6. Work sequence

### M0 — Receive the manual baseline and findings

- Treat the reviewed 3.1.1 manual content as the private, reproducible baseline
  for the code review.
- Receive a bounded inventory of code-relevant findings from the documentation
  thread without editing `orb.js-docs` in this workstream.
- Confirm that each finding identifies its 3.1.1 behavior, intended contract,
  and supporting page, example, or review evidence.
- Confirm the intended stable manual URL before package-local 3.2 links are
  frozen.
- Do not require or perform a separate public 3.1.1 manual launch. The first
  public detailed-manual release is coordinated with 3.2.

Exit condition: the code work has a reproducible 3.1.1 reference and a bounded
finding set, while documentation implementation and publication remain owned
by the documentation thread.

### M1 — Inventory findings and freeze the implementation scope

- Review the code-relevant public-API and runnable-example findings received
  from the documentation thread.
- Maintain a bounded code-side findings inventory using the intake fields
  above.
- Resolve duplicate, prose-only, and speculative findings.
- Identify changes that belong in 3.1 and route them through the maintenance
  line.
- Approve the exact 3.2 implementation set, including any decision needed for
  `propagateTwoBody` reflection and diagnostics.
- Record deferred ideas separately without making them release gates.

Exit condition: every 3.2 item has evidence, compatibility analysis, tests,
documentation impact, and an explicit disposition.

### M2 — Implement accepted 3.2 corrections on `v3`

For each accepted item:

- add or update the focused regression and API-contract tests first;
- make the smallest maintainable source change;
- preserve synchronous legacy behavior and existing defaults;
- update package exports or committed `dist/` only when the affected surface
  requires it;
- update concise package-local documentation and migration/release notes; and
- run focused tests followed by the full repository suite.

For the two-body naming change, verification includes:

- both named imports resolve from `@lizard-isana/orb/kepler` in the exact
  packed artifact;
- `propagateKepler === propagateTwoBody`;
- both names produce identical elliptic, parabolic, and hyperbolic results;
- existing `propagateKepler` examples and consumers continue to pass;
- invalid-input and non-convergence behavior remains compatible; and
- the reviewed API inventory identifies `propagateKepler` as an alias of
  `propagateTwoBody`.

Exit condition: all accepted source changes are complete on `v3`, focused and
full tests pass, generated artifacts are synchronized, and no unaccepted
finding has entered the release.

### M3 — Build the exact 3.2 documentation input

- Produce one exact artifact from the verified `v3` commit in an isolated
  release-preparation workspace. Give that artifact an explicit valid 3.2
  prerelease version; do not commit a routine development-version bump to
  `v3` merely to build documentation.
- Record its version, commit, integrity/checksum, export inventory, and packed
  file list, release notes, and tarball in the handoff to the documentation
  thread.
- Require the documentation work to identify that exact artifact rather than a
  moving local checkout or npm `latest`.
- Receive a verification report covering generated API facts, reviewed alias
  relationships, semantic contracts, runnable examples, and representative
  visual output.
- Route any runtime or public-API discrepancy discovered during that validation
  back through the finding-intake criteria. Rebuild and re-identify the
  artifact after every accepted source correction.
- Keep the detailed manual unpublished as stable until the coordinated 3.2
  release. Internal draft or preview mechanics remain owned by the
  documentation thread.

Exit condition: the documentation owner reports production readiness against
the same exact 3.2 artifact recorded by the code release, with no unresolved
contract or example mismatch.

### M4 — Code freeze and release-candidate verification

- Freeze the accepted scope on `v3` and cut `release/3.2`.
- Synchronize the release version in `package.json` and the lockfile only as
  part of release preparation.
- Run the full supported Node matrix and the complete repository suite.
- Run `npm run build`, confirm committed `dist/` synchronization, and run
  `npm run vsop:check`.
- Treat `npm run bench` as same-environment regression information, not a
  timing-flaky release gate.
- Build from an isolated `git archive` and compare its generated artifacts
  with the release tree.
- Inspect the exact tarball and test CommonJS, ESM, browser UMD, structured
  subpaths, optional data modules, package metadata, and installation in fresh
  consumers.
- Receive the documentation thread's complete automated and representative
  visual-verification results against the exact release candidate.
- Execute real Firefox and WebKit/Safari coverage required by the declared
  browser support, not only Node or Chromium approximations.
- Run a fresh dependency/advisory query immediately before publication.
- Review known issues and write release notes identifying aliases, behavior or
  numerical changes, documentation changes, and any migration advice.

Exit condition: the release candidate, tarball, documentation input, generated
artifacts, and recorded commit all agree, with no unresolved release blocker.

### M5 — Publish, verify, promote, and close

- Publish the exact verified 3.2.0 artifact to npm under `next`.
- Confirm registry metadata and integrity for that same artifact.
- Install `@lizard-isana/orb@next` in a clean consumer and repeat the relevant
  package and browser checks.
- Verify pinned CDN URLs for regular and minified browser artifacts.
- Confirm with the documentation owner that the verified 3.2 manual is ready
  for production deployment.
- Advance `master` to the verified release tree and promote the same npm
  artifact to `latest` only after the `next`, installation, CDN, browser, and
  documentation-readiness gates pass.
- Signal the documentation owner to publish the 3.2 detailed manual
  immediately after `latest` identifies 3.2.0, then verify the package-local
  manual link and release identity on the deployed site.
- Record the tag, commit, npm integrity, CDN results, documentation deployment,
  and final dist-tags in the release review.
- Treat `release/3.2` as the supported patch line and freeze `release/3.1`
  unless a separate extended-support decision is accepted.

Exit condition: npm `latest`, `master`, the release tag, installed package,
CDN artifacts, and the hosted manual all identify and verify the same 3.2.0
release.

## 7. Required verification baseline

Every implementation checkpoint runs checks proportional to its changes. The
full release baseline includes:

```sh
npm test
npm run build
npm run vsop:check
npm run bench
git diff --check
```

It also includes:

- focused domain and compatibility tests;
- exact-tarball consumer tests;
- generated `dist/` comparison;
- isolated clean-tree or archive verification;
- supported Node-version CI;
- real-browser verification for affected browser surfaces;
- fresh npm advisory checks;
- recorded evidence from the documentation thread that its clean installation,
  full check, links, search, locales, examples, and representative visual
  inspection passed against the exact package; and
- publication-time registry, installation, CDN, and dist-tag verification.

Benchmarks remain informational unless a separately accepted performance
contract defines a stable environment and threshold.

## 8. Release acceptance criteria

Version 3.2 is ready only when:

- the reviewed 3.1.1 manual baseline and its code-relevant findings are
  reproducible without requiring a separate public 3.1.1 launch;
- every runtime change traces to an accepted documentation finding or required
  release-maintenance task;
- existing public APIs, defaults, and synchronous behavior remain compatible;
- `propagateKepler` remains supported if `propagateTwoBody` is introduced;
- traceability code and contracts are absent from the 3.2 release scope;
- package-local and detailed documentation agree on names, units, frames,
  centers, time scales, models, validity, defaults, errors, and aliases;
- all runnable documentation examples pass against the exact release artifact;
- source, committed distributions, tarball, tag, registry package, CDN files,
  and documentation provenance identify the same release;
- the full automated, package, browser, documentation, visual, and audit gates
  pass;
- the release is not considered complete until both npm `latest` and the
  deployed detailed manual identify 3.2.0; and
- release notes distinguish compatible additions, corrections, documentation
  changes, known limitations, and deferred work.

## 9. Deferred decisions

The following remain open until the corresponding milestone supplies evidence:

- the complete set of 3.2 corrections beyond `propagateTwoBody`;
- the reflective `Function#name` and diagnostic-label treatment for that
  alias;
- whether any documentation finding requires a 3.1 maintenance fix first;
- the stable-site version-navigation model, which is owned by the documentation
  thread but must be reported as release-ready; and
- whether any candidate finding is important enough to justify a public API
  addition rather than a documentation-only clarification.

None of these open decisions reintroduces traceability into the 3.2 scope.
