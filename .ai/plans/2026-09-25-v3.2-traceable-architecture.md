# orb.js v3.2 traceable architecture proposal

Status: Draft / architecture review

Target branch: `v3`

Target release: a backward-compatible v3 minor release, currently planned as
3.2.0

Implementation status: not started. This document defines the design and PoC
gates; it is not implementation approval.

## 1. Context

Version 3.1.1 is the current stable release. The `v3` branch is the integration
line for the next backward-compatible v3 minor release. New 3.2 features and
maintenance refactors belong on `v3`; focused 3.1 fixes continue separately on
`release/3.1` and are forward-ported when applicable.

An earlier `v4-planning` prototype, now preserved as
`archive/v4-prototype`, explored embedding educational structure, explanatory
text, synchronized excerpts, and annotated-source tooling in the calculation
library. That approach made ordinary implementation changes substantially
harder to maintain. The existing decision to keep educational material outside
the runtime repository remains in force.

The new proposal addresses a narrower problem: make the meaning of a
calculation observable without turning the calculation source into a
textbook. A traceable distribution should expose the semantic stages actually
used for a calculation while preserving the normal result.

The motivating consumer is an astronomical-calculation reference site, but
the same structured trace should also support:

- debugging and numerical-difference investigation;
- model, option, and version comparisons;
- regression diagnosis;
- interactive demonstrations;
- structured context for AI systems; and
- auditable links between a result, the selected models, and the
  implementation that produced it.

## 2. Goal

Add an optional traceable surface that can answer questions such as:

- Which astronomical operations were performed?
- Which path through the calculation was selected?
- Which frame, center, unit, and time scale applied at each meaningful stage?
- Which corrections and models were applied, skipped, or unavailable?
- Which small set of intermediate values explains the final result?
- Where did two otherwise similar calculations begin to differ?

The trace is not a dump of local variables and is not a natural-language
explanation. It is a stable, structured account of the calculation's semantic
execution path.

The intended ownership boundary is:

```text
orb.js core
  owns calculation algorithms, numerical behavior, and orchestration

traceable surface
  owns observation, semantic operation identifiers, trace schema, and
  serialization

reference site or other consumer
  owns prose, equations, diagrams, exercises, and presentation
```

## 3. Meaning of "minimal core change"

The objective is not to minimize changed lines at any cost. A core change is
acceptable when all three conditions hold:

1. It does not obstruct or alter normal operation.
2. It does not materially enlarge the standard distribution.
3. It does not reduce maintainability.

These conditions imply the following gates.

### 3.1 Normal-operation gate

- Existing public APIs, defaults, result fields, errors, and synchronous
  behavior remain compatible.
- Importing a normal entry does not create a trace collector.
- Normal calculation does not depend on trace schema or trace metadata.
- No module-global mutable collector is added to the normal or traceable path.
- Invocation state is isolated so nested or re-entrant synchronous calls do
  not share trace state accidentally.
- Numerical and structural parity between normal and traceable results is
  tested automatically.

### 3.2 Size gate

- Trace schema, semantic catalogs, serializers, and presentation strings stay
  outside normal entries.
- The default UMD bundle contains no trace collector, schema, or explanatory
  strings.
- Optional structured entries include only the small shared calculation seam
  required by their ordinary implementation.
- The PoC is ESM-first. A second full UMD traceable bundle is deferred until a
  direct-script use case justifies its package-size cost.

### 3.3 Maintenance gate

- A high-level algorithm has one orchestration implementation.
- A numerical formula has one calculation implementation.
- The traceable surface must not recompute a result in order to explain it.
- Trace operation identifiers describe stable domain meaning rather than the
  current file layout or helper names.
- Normal and traceable surfaces are developed and verified in the same source
  tree and released at the same package version.

## 4. Why an external wrapper alone is insufficient

A wrapper around a public function can reliably observe its arguments, result,
and thrown error. It cannot reliably determine private branch choices,
internal frame paths, solver behavior, or skipped corrections when those
details are hidden behind lexical module bindings and local helpers.

An external-only design would therefore have to choose one of two undesirable
approaches:

- reproduce the high-level algorithm in the wrapper; or
- transform or patch the implementation at build time based on its current
  source shape.

The first duplicates calculation logic. The second couples traceability to
file names, source positions, and implementation details. Both make ordinary
orb.js upgrades more likely to break traceable behavior silently.

The preferred compromise is a small, intentional operation boundary in the
core calculation module. The core remains unaware of collectors, schemas, and
educational content; it only receives the operations used by one shared
orchestration engine.

## 5. Proposed architecture

### 5.1 Shared engine and injected operations

For a selected high-level module, extract its orchestration into an internal
engine that is constructed with a narrow set of meaningful operations.

Conceptually:

```js
const normalCreateObserver = createObserverEngine(normalOperations);
const tracedCreateObserver = createObserverEngine(tracedOperations);
```

The engine owns sequencing, option handling, branch selection, and result
assembly. Normal operations call the existing numerical implementation.
Traced operations delegate to exactly those same functions, record a semantic
step, and return the original value.

The operation boundary should be coarse enough to remain meaningful and
stable. For observation, likely candidates include:

- resolve a geocentric body state;
- transform a state between frames;
- form the observer-relative ECEF vector;
- convert ECEF to ENU;
- convert ENU to horizontal coordinates; and
- apply atmospheric refraction.

Individual additions, multiplications, trigonometric calls, VSOP87 terms, and
matrix elements are below the default trace boundary.

### 5.2 Dependency direction

The dependency direction remains:

```text
orb.js calculation implementation
             ↑
traceable facade and decorated operations
             ↑
debugger / AI consumer / reference site
```

The normal calculation implementation does not import the traceable runtime.

### 5.3 Proposed source layout

The exact file names remain subject to implementation review, but the intended
separation is:

```text
src/observer/
  engine.js          shared high-level orchestration
  operations.js      normal numerical operations
  index.js           normal public facade

src/traceable/
  runtime.js         invocation-scoped collector and trace association
  schema.js          orb-trace schema helpers
  serialize.js       deterministic JSON-safe serialization
  observer.js        traced observer operations and public facade
```

Trace-specific code must not be imported by `src/observer/index.js` or by the
default root entry.

### 5.4 No global collector

The trace collector must be created per root invocation. A process-wide or
module-wide "current trace" makes nested calls, tests, and future asynchronous
composition unsafe.

The shared engine may receive an invocation-scoped operation set or an
internal execution context. The normal facade uses a context-free or no-op
specialization. The traceable facade owns the collector lifecycle.

### 5.5 Source annotation convention

Shared normal/traceable seams are package-internal contracts rather than
public user APIs. When the 3.2 implementation introduces such a seam, document
it using JSDoc-formatted prose, the standard `@package` tag, and the single
orb.js-specific marker:

```js
/**
 * Shared orchestration boundary for normal and traceable observers.
 *
 * Changes require normal/traceable parity review.
 *
 * @package
 * @orbContract traceable
 */
```

The tag supplements rather than replaces the explanatory prose. It is a source
readability and optional checking convention; the documentation site does not
parse orb.js JSDoc comments or generate reference prose from them. Do not add
broader custom-tag vocabulary unless repeated implementation needs demonstrate
that standard JSDoc tags and the runtime-owned API contract are insufficient.

## 6. Distribution and import contract

### 6.1 Same package and version

The first implementation should remain in `@lizard-isana/orb` rather than use
an independently versioned package. Lockstep publication prevents a traceable
adapter from being paired accidentally with an incompatible core release.

The initial proposed entry is:

```js
import {
  createObserver,
  Trace
} from "@lizard-isana/orb/traceable/observer";
```

The normal equivalent remains:

```js
import {
  createObserver
} from "@lizard-isana/orb/observer";
```

The traceable observer entry must re-export the supported normal observer
surface and replace only the instrumented facade. CI compares the public
exports of the two entries, allowing only documented trace additions.

### 6.2 Do not promise a root replacement initially

The current package root is a legacy-compatible ESM/UMD surface, while the
modern APIs are separate ESM subpaths. A root-level
`@lizard-isana/orb/traceable` import would imply much broader compatibility
than an observer PoC can establish.

Start with an explicit `traceable/observer` entry. Add other traceable
subpaths only after the architecture passes the PoC gates. A root aggregator
may be considered after its complete export and behavior contract is defined.

### 6.3 Release-level compatibility promise

The realistic maintenance promise is not that every core refactor requires
zero traceable work. It is:

> A released orb.js version must not contain a traceable surface that is
> silently incompatible with its corresponding normal surface.

Parity and trace-contract tests must fail before an incompatible artifact can
be released.

## 7. Result and trace access

### 7.1 Compatibility levels

The compatibility contract distinguishes three levels:

1. Numerical and domain parity: required.
2. Enumerable-field and JSON parity: required where the normal result is
   JSON-serializable.
3. Full reflective equivalence: not promised when a discoverable `trace`
   property is present.

A non-enumerable property preserves `Object.keys()` and ordinary
`JSON.stringify()` output, but it remains visible to `in`, `Reflect.ownKeys()`,
and property-descriptor inspection. The documentation must not describe this
as complete observational identity.

### 7.2 Frozen results

Modern observer and event results are commonly frozen. A wrapper cannot append
a property after the normal call returns. For a supported plain-object or
array result, the traceable facade may:

1. make an equivalent outer copy;
2. define a non-enumerable, read-only `trace` property;
3. associate the result with the same trace in a side table; and
4. freeze the outer result when the normal result was frozen.

The normal field values and nested calculation objects are not recomputed.

### 7.3 Canonical and convenience access

The proposed access model is:

```js
const result = site.observe(body, instant, options);

result.trace;       // convenience for supported high-level object results
Trace.get(result);  // canonical association lookup
```

Primitive-returning APIs must not be changed into object-returning APIs. An
explicit capture form is reserved for primitive results, errors, and advanced
composition:

```js
const captured = Trace.capture(() => somePrimitiveCalculation());
// captured.result / captured.trace, or a structured error outcome
```

The precise error form is an open PoC decision. It must not change the error
type or message of the drop-in traceable API.

### 7.4 Explicit serialization

Because `trace` is non-enumerable and may also be held in a side table, AI and
log consumers use an explicit serializer:

```js
Trace.serialize(result);
```

Serialization must be deterministic and must not traverse arbitrary object
graphs indiscriminately.

## 8. Semantic trace contract

### 8.1 Trace is an execution account, not a call log

The trace describes domain operations and meaningful decisions. It may report
both applied and skipped operations:

```js
{
  operation: "observer.annual-aberration",
  status: "skipped",
  reason: "option-disabled"
}
```

For a bounded solver, the default trace should record a summary such as the
algorithm, convergence status, iteration count, final residual, and fallback
use. It should not emit every iteration unless a later detailed level is
explicitly requested.

### 8.2 Stable identifiers

Operation identifiers must describe domain meaning rather than current helper
names. A refactor that combines matrices, renames a source file, or reorganizes
private helpers should not require a schema change when the astronomical
operation remains the same.

Model identity is separate from operation identity. For example:

```js
{
  operation: "frames.transform",
  algorithm: {
    id: "precession-nutation",
    model: "iau2006-2000b",
    revision: 1
  },
  from: "equatorial-j2000",
  to: "equatorial-of-date"
}
```

When a numerical model changes, the model or revision changes even if the
trace schema and operation identifier remain stable.

### 8.3 Initial schema direction

The initial schema should support at least:

```js
{
  schema: "orb-trace/0",
  operation: "observer.observe",
  status: "ok",
  meta: {
    orbVersion: "3.2.0",
    traceVersion: "0.x"
  },
  level: "semantic",
  steps: [
    {
      id: "s1",
      parentId: null,
      operation: "observer.resolve-body-state",
      status: "applied",
      algorithm: { id: "...", model: "...", revision: 1 },
      inputs: { /* normalized descriptors */ },
      output: { /* normalized descriptor */ }
    }
  ],
  limits: {
    maxSteps: 100,
    truncated: false
  }
}
```

`id` identifies one occurrence. `operation` identifies stable meaning. A
hierarchy is represented by `parentId`; explicit `dependsOn` edges may be
added where data dependency cannot be inferred from the hierarchy.

The production schema begins at `orb-trace/1` only after the PoC has validated
its shape. `orb-trace/0` may change freely during the feature branch.

### 8.4 Value normalization

Trace values must be deliberately summarized.

- `AstroInstant` records normalized UTC and the time-scale values needed by
  the operation.
- `Date` records an ISO value.
- Typed arrays record their numeric values and semantic vector or matrix role.
- State vectors retain time, frame, center, units, position, and velocity only
  when relevant to the step.
- Body objects are represented by a name, model/provenance summary, and stable
  role; methods and complete internal objects are not serialized.
- Large coefficient tables, complete SGP4 local state, functions, cyclic
  graphs, and arbitrary application objects are not traversed by default.
- Non-finite numbers receive an explicit JSON-safe representation.

No natural-language teaching text, LaTeX, or site-specific presentation data
belongs in the trace schema.

### 8.5 Size and detail controls

The default level is semantic. The schema must be able to report truncation
and configured limits. Possible later levels include `summary` and `detailed`,
but the PoC should not promise them until a real consumer demonstrates the
need.

Events, VSOP87 evaluation, and SGP4 can generate large traces if every sample,
term, or local variable is recorded. Their default trace, if added later,
must summarize repeated work rather than emit it in full.

## 9. Current-code observations

The v3.1 structured surface already provides most low-level operations needed
for a first semantic trace:

- `time` provides `AstroInstant` and explicit UTC/UT1/TT handling;
- `frames` provides frame transforms, matrices, sidereal time, precession,
  nutation, and vector operations;
- `geodesy` provides WGS-84, ECEF, ENU, and horizontal conversion;
- `kepler` provides Stumpff functions, universal-variable propagation, and
  state/element conversion;
- `observer` composes body state, corrections, frame transforms, parallax,
  horizontal conversion, and optional refraction; and
- `vocab` and model provenance already carry part of the semantic vocabulary.

Therefore v3.2 should not broadly export private helpers merely to support
tracing. A low-level function becomes public only when it has independent
astronomical or mathematical value, a stable input/output contract, and a
credible long-term compatibility story.

Specific constraints from the current implementation include:

- `createObserver()` statically imports meaningful frame, geodesy, apparent,
  and refraction operations and freezes both the site and result;
- legacy `Observation.azel()` contains more inline orchestration and local
  conversion paths, making it a poor first PoC target;
- the universal-anomaly solver is private and useful for trace summaries, but
  public exposure would create an unnecessary solver-contract commitment;
- event searches return frozen arrays and can call observation functions many
  times; and
- the current Rollup build produces the legacy root bundle and compatibility
  preflight, while structured subpaths are published as ESM source modules.

These observations favor a modern-observer ESM PoC over legacy-root,
event-search, or full-bundle instrumentation.

## 10. Implementation approaches considered

### 10.1 Shared engine with injected operations — preferred

Advantages:

- one high-level algorithm;
- one numerical implementation;
- explicit and testable semantic seams;
- no source-position dependency;
- trace-specific code stays outside normal entries; and
- compatible with lockstep normal and traceable subpaths.

Costs:

- a small core refactor;
- possible indirect-call overhead in the normal structured module; and
- discipline is required to keep the operation boundary semantic rather than
  excessively granular.

The overhead must be measured rather than assumed. If it is material, normal
operations may be captured once when constructing the engine or otherwise
specialized without duplicating the orchestration.

### 10.2 Module wrappers plus build aliasing — secondary option

This can leave calculation source unchanged, but the current build does not
bundle all structured subpaths. Alias rules also depend on import layout and
must avoid wrappers re-importing themselves. It remains useful for an
experiment but is not the preferred stable architecture.

### 10.3 Public operation registry — not preferred

A registry increases mutable global configuration, ordering questions, and
cross-application interference. It also gives normal applications a broad
extension point that is not otherwise required.

### 10.4 Build-time source transformation — experimental only

Instrumentation transforms can guarantee zero runtime hook in a normal
build, but they couple the trace build to syntax and source structure, make
sourcemaps and debugging harder, and introduce additional build dependencies.
Use only for a disposable comparison if the preferred approach encounters a
specific blocker.

### 10.5 Copied high-level algorithms — rejected

Do not copy `observe()`, `azel()`, propagation, or frame-routing algorithms
into a traceable implementation.

## 11. Observer PoC

### 11.1 Scope

The first PoC targets only the modern observer surface:

```text
@lizard-isana/orb/observer
@lizard-isana/orb/traceable/observer
```

It must cover at least:

- the geometric, airless default;
- heliocentric and geocentric body states;
- frame conversion to Earth-fixed coordinates;
- observer-relative topocentric geometry;
- ENU and horizontal conversion;
- light time enabled and disabled;
- annual aberration enabled and disabled;
- refraction enabled and disabled; and
- result metadata enabled and disabled.

### 11.2 Minimum useful trace

The trace must be sufficient for a reference site to render:

1. the input time and observer context;
2. the selected body-state model and provenance;
3. the geocentric/apparent correction choices;
4. the frame path used;
5. the topocentric subtraction and diurnal-parallax stage;
6. the horizontal conversion;
7. the refraction decision; and
8. the final quantities with unit, frame, center, and applied-correction
   meaning.

The PoC does not need every vector at every stage. It should include only the
values needed to explain or compare the operation.

### 11.3 Reference-site validation

Before expanding coverage, build or prototype one consumer view capable of
showing:

- the calculation flow;
- actual values at the semantic stages;
- correction on/off differences;
- the algorithm/model identifiers; and
- links from stable operation identifiers to external explanation and the
  versioned implementation.

If the view cannot explain the calculation without reaching into private
orb.js objects, the schema is incomplete. If the trace overwhelms the view
with irrelevant values, the boundary is too fine.

## 12. Verification contract

### 12.1 API parity

- Compare normal and traceable public exports for the supported subpath.
- Keep function signatures and ordinary call patterns compatible.
- Allow only documented additions such as `Trace`.

### 12.2 Result parity

For identical input:

```text
normal result == traceable result with trace association removed
```

Tests cover:

- scalar fields;
- typed-array contents;
- nested metadata;
- enumerable keys;
- ordinary JSON output;
- prototypes where applicable;
- frozen/extensible state; and
- errors, including type and message.

Floating-point comparisons use the same tolerance policy as the corresponding
normal API. When both surfaces invoke exactly the same implementation, strict
numeric equality is preferred.

### 12.3 Trace contract

- The root operation and schema version are present.
- Expected semantic operations appear for each option path.
- Applied and skipped corrections are distinguishable.
- Step identifiers are unique.
- Parent and dependency references are valid.
- Units, frames, centers, time scales, and models use controlled values where
  available.
- Serialization is deterministic.
- Trace limits and truncation are explicit.
- Failed calculations retain a useful trace without changing the drop-in
  error contract.

### 12.4 Standard-build isolation

- The default UMD bundle contains no trace schema, operation catalog,
  serializer, or explanatory strings.
- For the observer-only PoC, the default root bundle should remain byte-for-
  byte unchanged unless an independently justified core change reaches that
  bundle.
- Normal and traceable sizes are reported separately.
- Exact npm-tarball tests verify that new exports resolve correctly and that
  ordinary existing consumers remain unchanged.

### 12.5 Performance

Performance measurements are regression information, not timing-flaky CI
gates. Record:

- normal observer throughput before and after the shared-engine refactor;
- traceable observer throughput;
- trace construction and serialization cost; and
- representative trace size.

Any material normal-path regression requires redesign or an explicit review;
traceable overhead is acceptable when bounded and documented.

### 12.6 Existing repository gates

Implementation work continues to run, as applicable:

- the full test suite;
- focused milestone/domain tests;
- the build;
- deterministic VSOP verification;
- package and exact-tarball consumers;
- browser checks for affected entry types;
- syntax and whitespace checks; and
- non-gating benchmarks.

## 13. Proposed work sequence

### A. Contract inventory

- Record the exact exports and result shapes of the selected normal subpath.
- Record freeze, enumeration, serialization, error, and prototype behavior.
- Identify the semantic operations already present in the implementation.
- Confirm that no unrelated worktree changes are mixed into the effort.

### B. Trace schema v0 and parity harness

- Implement or prototype the invocation-scoped collector.
- Define deterministic value descriptors and serialization.
- Establish normal/traceable result comparison before adding deep coverage.
- Establish export-parity checks.

### C. Shared observer engine

- Extract only the orchestration needed for the observer PoC.
- Inject a narrow normal operation set.
- Prove that normal results, errors, and metadata remain unchanged.
- Measure normal-path size and performance before proceeding.

### D. Traceable observer facade

- Decorate the same normal operations.
- Associate a semantic trace with the high-level result.
- Cover applied, skipped, and error paths.
- Add the traceable package export and exact-tarball consumer tests.

### E. Consumer validation and architecture decision

- Render one reference-site calculation flow from the trace.
- Compare corrections or models using two traces.
- Evaluate readability, trace size, maintenance cost, and normal-path impact.
- Decide whether to stabilize `orb-trace/1`, revise the architecture, or stop.

### F. Optional expansion

Only after the observer PoC passes may work consider:

- `traceable/kepler`, with semantic solver summaries;
- frame-transform tracing;
- SGP4 input/propagation summaries;
- bounded event-search summaries;
- a root traceable aggregator; or
- a browser-ready traceable UMD build.

Each expansion requires its own result and size inventory. Success for
observer does not automatically authorize tracing every module.

## 14. Acceptance criteria

The architecture is accepted for stabilization only if all of the following
hold:

- Existing normal observer API and numerical behavior remain compatible.
- A traceable observer import can replace the normal observer import for the
  documented surface.
- Normal and traceable calculations share the same orchestration and numerical
  implementation.
- The trace reports semantic stages rather than low-level execution noise.
- A reference-site consumer can explain one real calculation from the trace
  without private implementation access.
- The default UMD has no trace-specific runtime or size increase.
- The normal structured observer has no material unreviewed performance or
  size regression.
- Frozen results, enumerable keys, ordinary JSON, and errors follow the
  documented compatibility contract.
- Normal/traceable API drift and result drift fail CI.
- Schema versioning is independent from the orb.js API version.
- No educational prose, equations, or site assets enter the runtime library.

## 15. Stop or redesign conditions

The PoC must stop or reduce its trace granularity if any of the following is
required:

- copying a high-level algorithm;
- recomputing a result solely to explain it;
- adding a broad mutable registry or global collector;
- placing substantial trace metadata or strings in the normal bundle;
- publishing unstable private helpers solely for trace access;
- coupling stable trace IDs to file names, line numbers, or helper names;
- recording unbounded loop, term, or event-sampling detail by default;
- changing primitive results into wrapper objects; or
- making ordinary orb.js refactors require synchronized educational prose.

## 16. Non-goals

The initial 3.2 work does not attempt to provide:

- a complete trace of every public API;
- every intermediate numerical value;
- VSOP87 term-by-term output;
- SGP4 local-variable dumps;
- event-search sample-by-sample output;
- natural-language explanations;
- embedded lessons, LaTeX, diagrams, or exercises;
- a stable `orb-trace/1` schema before consumer validation;
- a root package import replacement;
- an independently versioned trace package; or
- a permanent second development branch for traceable code.

## 17. Open decisions for the PoC

The following remain deliberate PoC questions rather than implicit contracts:

- whether `Trace.get(result)` or `result.trace` is the primary documented form;
- the exact structured outcome for `Trace.capture()` when the calculation
  throws;
- whether the first trace stores selected vectors or only summarized values;
- the operation-ID naming convention and catalog location;
- the initial maximum step and serialized-size limits;
- whether `summary` and `detailed` levels are needed beyond `semantic`;
- whether traceable subpaths should share one `Trace` singleton per module
  graph or expose interoperable runtime instances; and
- what measured normal-path overhead is considered material.

These questions should be answered from the observer PoC and reference-site
consumer, not by designing all future modules in advance.

## 18. Expected v3.2 outcome

A successful v3.2 traceable effort would establish:

- a small reusable observability seam for selected structured calculations;
- a versioned semantic trace contract;
- a compatible ESM traceable observer entry;
- deterministic serialization for debugging and AI consumers;
- automated normal/traceable drift detection; and
- evidence from a real reference-site view that the trace adds explanatory
  value without moving educational responsibility into orb.js.

The feature should be described as making orb.js calculations semantically
observable, not as embedding education or exposing every internal detail.
